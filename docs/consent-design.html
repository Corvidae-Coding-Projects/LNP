Older LNP design draft

Consent without passwords

This draft explored whether Linux could safely approve a small system change with a protected click instead of a password. It is not the current LNP security design.

01 — Problem

What a click has to be worth

Every privileged action in LNP currently costs an administrator password. That is friction in the wrong place: on a single-user laptop the person already proved who they are at login. What the system actually needs at the moment of elevation is proof of intent — that a human, not a background process, decided this should happen.

Windows solved this with the UAC consent prompt, and the reason a bare click is trustworthy there has nothing to do with the dialog's appearance. consent.exe runs as SYSTEM on a separate desktop object. Processes on the interactive desktop cannot post input to it, cannot screenshot it, and cannot draw a convincing forgery over it. Malware can provoke a prompt; it cannot answer one.

That specific trick does not port. On Linux the compositor runs as the user — the same user malware would run as. There is no SYSTEM-owned desktop to escape to. Copying the dialog without copying the anchor produces something that looks like UAC and protects nothing.

02 — Rejected approach

Why a custom agent is not the answer

polkit lets anyone register an authentication agent. We could ship one that shows a Yes/No dialog for our actions and delegates everything else to the password flow, and it would work today with no patches at all. It is the obvious shortcut and we should not take it.

The agent's job is to authenticate a user and report the result to polkitd via AuthenticationAgentResponse2. polkitd cannot verify that a PAM conversation actually happened; it trusts the registered agent. An agent that returns success without authenticating is asserting something untrue to the security daemon. It works precisely because of a trust gap, and it leaves the policy file lying too — the action would still read auth_admin while no admin was ever authenticated.

The result is indistinguishable, to an auditor reading the policy, from a system that asks for a password. That is a worse property than simply setting the action to yes, which at least tells the truth.

03 — Threat model

What this defends against, and what it does not

In scope

  • An unprivileged process invoking a privileged action silently. It may provoke a prompt; it must not be able to answer one.
  • A malicious client forging or overdrawing the consent surface. Covered by Part C.
  • Input synthesis into the consent surface. Wayland already forbids client-to-client input injection; the one escape hatch, org_kde_kwin_fake_input, is itself gated by the mechanism Part C builds on.
  • Password theft by a hostile agent. Removing the password from the common path removes the thing worth stealing.

Not covered by this draft

  • A user who is socially engineered into clicking. No consent mechanism, on any operating system, survives a person who decides to say yes. UAC does not solve this either.
  • Malware already running as the user, targeting the user's own files. Those are readable without any elevation. This design protects the system, not the home directory.
  • A compromised compositor. KWin already sees every keystroke and frames every pixel. If it is hostile, nothing in the session is salvageable, and anchoring to it costs nothing we still had.
Stated plainly

Following Microsoft's own precedent, we should say which actions this protects and which it merely documents. UAC shipped as an awareness feature, was widely read as a boundary, and fifteen years of auto-elevation bypasses went unpatched because the two were never separated in public. We separate them in §07.

04 — Part B

An honest consent mode in polkit

The goal is a new implicit-authorization value, auth_consent, that means exactly what it says: prompt a human for a yes-or-no decision, require no credential, and grant on yes. Crucially, polkitd remains the gate throughout — nothing about this lets a caller bypass the check, and no component misrepresents what it did.

Verified on this machine

polkit 127 exposes the enum as POLKIT_IMPLICIT_AUTHORIZATION_* with polkit_implicit_authorization_from_string and …_to_string as the string boundary, and today's policy files use only no, yes, auth_self, auth_admin, and the _keep variants. The extension point is narrow and well-defined.

Changes to polkit

  1. Enum. Add POLKIT_IMPLICIT_AUTHORIZATION_CONSENT_REQUIRED (and a …_RETAINED sibling, matching the existing _keep pattern) to the public enum.
  2. String boundary. Teach polkit_implicit_authorization_from_string / …_to_string the token auth_consent so .policy files can declare it and pkaction --verbose reports it.
  3. Authority. In the backend's decision path, route the new value to an authentication session as the existing admin path does, flagged as consent-only — the branch that today chooses between "authenticate as self" and "authenticate as admin" gains a third outcome.
  4. Agent interface. The agent-facing BeginAuthentication call carries an identity list; a consent request carries an empty identity list plus a consent-only hint in its details map. An agent that does not understand the hint sees no identities to authenticate and must fail closed, which is the correct behaviour for an old agent meeting a new policy.
  5. Response. Reuse AuthenticationAgentResponse2 unchanged. The agent reports that the human consented; it never claims an identity was authenticated, because none was asked for.

Changes to polkit-kde-agent-1

Render a two-button dialog when the consent hint is present: the action message, the requesting application, and Allow / Deny. No password field, because there is nothing to type. This is also where Part C attaches — the dialog is presented through the consent surface rather than as an ordinary window.

05 — Part C

The compositor as trust anchor

A dialog is only as trustworthy as the guarantee that nothing drew over it, nothing synthesised its click, and nothing screenshotted what it showed. Exactly one process in a Wayland session can make those guarantees: the compositor. Part C is a small Wayland protocol, kde_consent_v1, through which KWin grants a surface those properties.

The mechanism already exists

KWin gates privileged interfaces by checking the client's credentials — wl_client_get_credentials, matched against a desktop file declaring X-KDE-Wayland-Interfaces, with wp_security_context for sandboxed clients. We have already used this in production in this project: it is how lnp-dock obtains org_kde_plasma_window_management. KWin also already ships kde_lockscreen_overlay_v1, so a compositor-granted privileged surface role is established practice, not a novelty. And the input-synthesis interface org_kde_kwin_fake_input sits behind the same gate — evidence KWin treats this list as a real boundary.

Protocol sketch

interface kde_consent_manager_v1
  request  get_consent_surface(new_id, wl_surface, cookie)
      cookie: the polkit authentication cookie, so the compositor
              can confirm with polkitd that a request is genuinely
              outstanding rather than fabricated by the client

interface kde_consent_surface_v1
  event    presented()          shown and holding exclusive input
  event    dismissed(reason)    user cancelled, or focus/session changed
  request  destroy()

While a consent surface is presented, KWin guarantees:

  • it is stacked above every other surface, including layer-shell;
  • all pointer and keyboard input routes to it exclusively, and fake_input events are dropped for its duration;
  • screencopy and portal capture of its contents are refused;
  • it is torn down on session lock, VT switch, or client death — a consent surface can never be left orphaned on screen.

Why the cookie matters

Binary-path checking answers "is this the real agent?" but not "is there really a request pending?". A stolen or replaced agent binary would defeat the first check alone. Having KWin confirm the cookie with polkitd means a consent surface can only appear when polkitd is genuinely waiting on an answer — the compositor and the authority have to agree before anything is drawn.

06 — Composed

What B and C buy separately

The two parts are independently useful, which matters for phasing. B without C gives an honest consent mode whose dialog is an ordinary window — better than today on friction and on password exposure, no better on spoofing. C without B would harden the existing password dialog against overdraw and capture, which is worth having on its own. Together they produce a click that is worth trusting.

PropertyTodayB onlyB + C
Caller can bypass the checkNoNoNo
Password exposed to a hostile agentYesNoNo
Dialog can be overdrawnYesYesNo
Click can be synthesisedYes†Yes†No
Policy file states the truthYesYesYes

† Only via org_kde_kwin_fake_input, which already requires a KWin trust grant. The realistic exposure today is overdraw and phishing, not synthesis.

07 — Application

Which of our actions get which treatment

The risk grading already built into lnp-selinux maps directly onto authorization modes. This is the table that says what is protected and what is merely documented.

ActionGradeModeReasoning
relabel Safe auth_consent Restores a label policy already defines. Near-zero grant, but not zero — a writer of a security-relevant path could gain a trusted label, so it keeps a prompt rather than becoming yes.
setbool Moderate auth_consent A documented, reversible, bounded policy switch. Consent is proportionate.
fcontext Moderate auth_consent Narrow and path-scoped, but it changes policy expectations persistently.
allow-module High auth_admin Permits precisely what was blocked. Keeps a password permanently — this is the one where a phished click would be worth stealing.
codecs · drivers High auth_admin Installs software from a third-party repository. Not a candidate.

Note what is absent: no action becomes yes. Silent elevation is how UAC's auto-elevation list became a bypass farm. Every privileged action in LNP should cost a human gesture; the design question is only which gesture.

08 — Cost

What this actually costs to own

The engineering is tractable. The maintenance is the real price, and it should be decided with open eyes.

  • Two carried patch sets, against polkit and polkit-kde-agent-1, rebased every Fedora release. Both are security-relevant components; a divergent polkit means partly owning its CVE response, and a delayed rebase means delaying security updates for the whole system.
  • A KWin plugin tracking a compositor whose internal APIs are explicitly unstable between releases. kwin-devel 6.7.4 is available; the plugin will break on major KWin updates, and a broken consent plugin must fail closed — falling back to the password dialog, never to silent grant.
  • A protocol we invented. Unless kde_consent_v1 is proposed upstream to KDE, it is ours forever and works on exactly one compositor.
The honest alternative

Upstreaming changes the calculus entirely. auth_consent is a coherent addition that other desktops would benefit from, and the compositor-anchored surface is a better answer to a problem GNOME and KDE both have. Carried patches are a cost; an accepted proposal is an asset. If we build this, we should build it to be proposed — which mostly means designing it as though somebody skeptical will review it.

09 — Not covered

What this deliberately is not

  • Not a replacement for authentication. Consent proves intent, never identity. Anything needing identity keeps a password.
  • Not a sandbox. It governs elevation, not what an already-elevated process does afterwards.
  • Not multi-user. The reasoning assumes one human at one laptop. A shared machine wants auth_admin throughout, and the policy should say so.
  • Not a claim to be unbypassable. If we ship this we state its boundary in the documentation, in the words above — and we do not repeat Microsoft's mistake of letting users infer a stronger promise than the one we made.
10 — Phasing

Order of work

Each phase is independently shippable and independently abandonable, which is the property that makes it safe to start.

  1. Prototype B against a local polkit build. No packaging, no system install — prove auth_consent flows end to end from .policy file through polkitd to a stub agent. This is where we learn whether the backend's decision path is as tidy as it looks from outside.
  2. Teach polkit-kde-agent the consent dialog. Still an ordinary window. At this point the friction problem is solved and the password is off the common path — most of the user-visible win, none of the compositor work.
  3. Add kde_consent_v1 to KWin behind the existing trust-grant mechanism. Exclusive input first, then capture refusal, then the cookie confirmation with polkitd.
  4. Move the agent's dialog onto the consent surface, with a hard fallback to the password path if the protocol is absent or the plugin refuses.
  5. Propose upstream. Which, if it succeeds, deletes most of section 08.
