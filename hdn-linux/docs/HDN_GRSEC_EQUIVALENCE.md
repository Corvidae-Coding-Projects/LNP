# HDN vs grsecurity Functional Equivalence Matrix

This document compares the current HDN Linux 7.0.12 hardening patch against
the grsecurity/PaX feature surface visible in the local `grsec-6.6.102.patch`.
It is a functional comparison only. HDN should keep using its own policy model,
call sites, tests, and implementation structure.

## Status Key

- Covered: HDN has a kernel mechanism and a smoke proof for the security effect.
- Covered (daily-driver semantics): HDN proves the security goal but
  intentionally does not reproduce behavior that would break ordinary desktop
  operation.
- Baseline: HDN relies on upstream Linux Kconfig/runtime mitigations selected
  by `SECURITY_HARDENING_EXPLOIT_MITIGATIONS`.
- Permanently deferred: intentionally excluded because the mechanism is an
  obsolete compatibility ABI, falls outside the x86_64 product target, is
  superseded by a proved upstream mechanism, or conflicts with the product
  security/usability model.

Every matrix row below has a final disposition. There are no untracked partial
or gap states in the release-scoped x86_64 daily-driver surface.

## Policy And Administration

Executable profile identity is persistent rather than credential-derived after
commit. QEMU proves that an executable-selected restricted profile survives a
same-user-namespace root-to-nonroot UID/GID drop; entering a new user namespace
still selects the namespace profile.

## Release Disposition

The x86_64 daily-driver matrix is closed. Exact grsecurity policy-language,
daemon, Kconfig, sysctl, group-selector, event-string, and other compatibility
ABIs are permanently deferred because HDN exposes its own signed policy and
typed product interfaces. Obsolete executable-memory emulation is permanently
deferred in favor of supported runtimes. Non-x86 thread-stack placement and
exact PaX/grsecurity compiler-plugin or architecture implementations are also
permanently deferred outside this release target; the selected and live-tested
upstream mitigation baseline is the release requirement.

Future policy operations, architectures, and compiler mechanisms may be added
as separately designed HDN features. They are expansion work, not unresolved
claims in this matrix.
